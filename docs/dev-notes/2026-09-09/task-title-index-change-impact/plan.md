## ゴール

`problem_index`（DB 上は `task_table_index`）に AOJ 問題 ID ではなく**問題記号**を持たせ、表示側が変換なしにそれを使える状態にする。

> **問題記号**: `A`, `B`, `C`… のように、そのコンテスト内で何番目の問題かを表す記号。AtCoder では `abc300_a` の `a` にあたる。AOJ には存在しない（難所 1）。コード上は `letter`。

|                           | 変更前                                   | 目標                                         |
| ------------------------- | ---------------------------------------- | -------------------------------------------- |
| **G1** 出典欄             | `AOJ 3467（ICPC 国内予選 2024）`         | `ICPC 国内予選 2024 - F（AOJ）`              |
| **G2** コンテストテーブル | 問題 ID 3467 → ソート位置から `F` を算出 | `task_table_index` の `F` を**そのまま使う** |

## 3 つの難所

**難所 1: 問題記号は AOJ API から取得できない。** API は「その問題がコンテストで何番目か」を返さない。ただし**基本ルール**（コンテスト内で問題 ID が若い順に `A`, `B`, `C`…）で復元できる。⇒ 対応表はスクリプトで機械生成できる。

**難所 2: 欠落があると基本ルールが破れる。しかも欠落はデータから検出できない。** ここでの欠落は、公式の問題が AOJ のコンテスト一覧（管理画面の取り込み元）に無いことを指す。AOJ に登録されていない問題なら ID も無いため、残った問題の ID は連番のままになる。AOJ に問題はあるのに一覧から外れている場合もある（ICPC 国内予選 2002 の E = AOJ 1123）。⇒ **コンテスト単位で外部情報（メンテナのスプレッドシート）と照合するしかない**。PR2 の範囲では、実際に 8 コンテストで先頭・途中の欠落が見つかった（[照合結果](./investigation.md#記号の補正が要るコンテスト)）。

**難所 3: 表示層で逃げられない。** 出典欄は `task_table_index` を直接読む。⇒ DB の値そのものを直す以外に手段がない。

## データ移行の共通手順

PR2（記号の移行）と PR2.1（enum の追加）、PR3 に当てはまる。

### CI での適用

`.github/workflows/ci.yml` の流れ（2026-10-24 に確認）:

1. `main` / `staging` への push と、`pull_request` で起動する
2. build / lint / check / unit-test が並列に走る
3. 4 つとも通ると、`main` 以外では `preview` ジョブ、`main` では `production` ジョブが走る。どちらも `vercel build` の**後**・Vercel デプロイの**前**に `prisma migrate deploy` を流す（build が失敗すれば DB に触れない）

| 起動したもの                                                | ジョブ       | 適用先                                  |
| ----------------------------------------------------------- | ------------ | --------------------------------------- |
| PR の CI（ref は `refs/pull/N/merge`）、`staging` への push | `preview`    | `PREVIEW_DATABASE_URL`（staging の DB） |
| `main` への push                                            | `production` | `PRODUCTION_DATABASE_URL`               |

- **PR の CI でも staging の DB に適用される**。PR を開いた瞬間ではなく、その PR の CI で 4 ジョブが通った後だが、**staging へのマージより前**である。`preview` ジョブの条件は `github.ref != 'refs/heads/main'` だけで、PR の ref も当たる。実際、#4217 の `pull_request` の実行でも `preview` ジョブが成功している（ログはログインしないと見られないので、`migrate deploy` の出力までは確かめていない）。staging へマージしたときにも走るが、適用済みなので何もしない
- このため SQL の確認は PR を開く前にローカルで済ませる。PR に push し直すたびに CI が走るが、適用済みのマイグレーションは編集しても再適用されない
- `main` へ昇格した時点で production に適用されるため、**staging での確認が自然にゲートになる**
- 本件の範囲外だが、`preview` ジョブの「Assign staging domain」の手順は、コメントに「if staging branch」とあるのに条件は `github.ref != 'refs/heads/main'` である。PR のデプロイにも staging のドメインが付け替わる

### 手順

1. `pnpm exec prisma migrate dev --create-only --name <name>`
2. SQL を `migration.sql` に書く
3. **ローカル DB で `UPDATE` を `SELECT` に置き換えて「現在値 → 変更後」を確認する**
4. ローカルで `pnpm exec prisma migrate dev` を実行して適用し、表示を確認する
5. PR を開く → staging へマージして確認 → `main` へ昇格

手順 3–4 は**必ず PR を開く前に**済ませる。PR を開いた時点で preview DB に適用されうるうえ、適用済みのマイグレーションは編集しても再適用されない。PR を開いた後に SQL の誤りが見つかったら、新しいマイグレーションを積む。

手順 3 により **SQL の正しさを構文から判断する必要がなくなる**。全件を見る必要はないが、**コンテストの切り替わり目（記号が `A` に戻る箇所）**と**問題数の少ない古いコンテスト**は目視する価値がある。

**staging が防げないもの**: **対応表・欠落判断そのものの誤り**。誤った記号でも SQL は正常に完走し、staging では「それらしい表示」になる（難所 2）。

### 事故対策

| 観点                     | 内容                                                                                                                                                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **爆発半径**             | 一括で復元できるのは AOJ ICPC / JAG だけ（`task_table_index == task_id` が成り立っていたため）。WHERE 句が壊れて AtCoder 系に波及すると**一括復元の手段が無くなる**（[実測](./investigation.md#復元可能性の実測)） |
| **復元**                 | 一度目の適用に限り、`task_table_index` も `title` のプレフィックスも `task_id` から再構成できる                                                                                                                    |
| **バックアップ**         | Supabase Pro のため PITR が利用可。復元トリックが効くのは一度目だけなので、**再修正時は PITR が唯一の手段**                                                                                                        |
| **`updated_at`**         | `@updatedAt` は Prisma Client 側の実装で DB トリガーではない。生 SQL では更新されない。**意図的に含めない**                                                                                                        |
| **キャッシュ**           | TTL 1 時間（`src/lib/clients/cache.ts`）。生 SQL と CSV の投入は `invalidateTaskCaches()` を経由しない。「更新したのに表示が変わらない」ときはこれを疑う                                                           |
| **トランザクション境界** | マイグレーションファイル単位で原子的に適用される（[done.md](./done.md#移行-sql)）                                                                                                                                  |
| **デプロイ直前の数分**   | マイグレーションの適用から Vercel のデプロイ完了までの間は、旧コードが新しいデータを描画する。数分で解消するので**許容する**                                                                                       |

### スプレッドシートとの照合

対応表は次の手順で作る（M6）。PR1 のスクリプトを直して使う（仕組みは [done.md](./done.md#照合記号の対応表)）。

1. 基本ルールで対象範囲の記号を生成する
2. コンテスト単位で、メンテナのスプレッドシートと照合する ← 人手が要るのはここだけ（書き写し）
3. 先頭・途中に欠落があるコンテストは、スプレッドシートの位置から記号を決める（末尾の欠落は記号がずれないので補正不要）
4. 欠落した問題が AOJ に問題番号で存在するかを確かめ、PR3 に引き継ぐ

> **注意**: 「これまで正しく見えていた」は「欠落が無い」の証明ではない。欠落があっても表示は成立してしまう（前詰めでずれた記号が出るだけ）。

**スクリプトには総数のアサーションを入れる。** 抽出漏れが欠落の誤検出に直結する（調査中に実際に踏んだ。[事例](./investigation.md#6-調査中の誤りと訂正自戒)）。抽出件数が対象範囲の既知の値と一致しなければエラーで止め、欠落として扱わない。
