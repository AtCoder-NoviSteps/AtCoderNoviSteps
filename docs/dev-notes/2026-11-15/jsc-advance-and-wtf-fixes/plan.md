## 決定事項

- **jsc2026advance-final はペアだけで表示する**（2025 と同じ）。分類が `null` のペアは黙って捨てられるので `ABC_LIKE` に足した。ABC-Like テーブルにも出る。
- **ペアの本番投入はデータ migration**（メンテナが選択）。却下: Supabase CSV（手作業で `id` / `updatedAt` を作り、キャッシュが切れるまで表示されないことがある）。
- **ABC 21 行は migration に入れない**: 本番に全行あった。
- **同じ大会の複数日は Day1, Day2, … の順**（メンテナの方針、テーブル共通）。ガイドに書いた。
- **`-open` は世界大会だけ外す**（メンテナが判断）。jsc2022-final-open / ajo2025-final-open / codequeen2023-final-open は対象外。
- **`stripOpenSuffix` は残す**: 管理画面の取り込みは AtCoder Problems の `-open` 付きの値で入る。テストは fixture を本体の形にし、`-open` 付きの形を分類とラベルの専用ケースで確かめる（計画の「fixture に両方を持つ」から変えた。同じケースを二重に持たないため）。
- **1 PR、`-open` は最後のフェーズ**: どちらも migration を含み、クロスレビューは 1 回で済む。

## コードと履歴に残らない事実

- **データ源**: AtCoder Problems の 21 行とペア 7 行はメンテナが貼った。13 行は `adt_*` の contest_id と ADT の記号だったので、task_id から本来の値に戻した。本体の URL（`awtf2025algo` など）もメンテナが示した。
- **本番の状態**（2026-11-15、メンテナが Supabase で確認）: abc412 / 464 / 474 の 21 行は、新しい seed と全項目一致。世界大会の contest_id は変更前の seed と一致（`-open` 付き 4 回で 21 行）。
- **sha256 は壊れない**: FK と回答・投票の ID はすべて task_id 基準。`Task.id`（取り込み時の `sha256(contest_id + task_id)`）を作り直したり、それで検索したりする処理は無い。
- **ローカルでの検証**: 本番と同じ状態の DB で、ペアの INSERT は 7 行が入り、再実行しても変わらない。UPDATE は contest_id だけが 21 行変わり、`id` などの他の列と総件数（4207）は変わらない。migration の後の `pnpm db:seed` で ABC 21 行が入り、ペアは 7 件のまま。
- **テストの検出力**: エントリの削除・入れ替え、seed の abc474_a の削除、ペアの記号の入れ替え、2025 の見出しの戻し、`stripOpenSuffix` の呼び出しの削除（分類・ラベル）のそれぞれでテストが落ちることを確かめた。
- **ゲート**: `pnpm format` / `lint` / `check` / `test:unit`（109 ファイル、3114 件）/ `git diff --check` はすべて成功。
- **クロスレビュー**（Codex、埋め込み方式）: Critical / Severe は 0 件。Minor 2 件（ペアの記号の対応・見出しのテストが無い）と、キャッシュの記述への疑問を、メンテナの選択で全部直した。キャッシュはプロセス内のメモリで、CI は migrate deploy の後に新しいデプロイを出すので、記述は正しい（理由をガイドに足した）。
- **表示**: `pnpm dev` でのテーブルの並び・見出しと、世界大会のリンクが本体を開くことは、メンテナが確認した（2026-11-15）。
