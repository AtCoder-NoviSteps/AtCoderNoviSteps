# E2E テストの高速化

## 概要

Playwright のインストールと E2E 実行に時間がかかる問題について、ツールを置き換えずに現行構成のまま短縮した。

採用したのは、起動済み preview サーバーの再利用（`reuseExistingServer`、9856264e）と、トレースの既定値を `off` にする変更（b8ec6d8e）の 2 つである。

その結果、2 回目以降の `pnpm test:e2e` は、起動待ち 15〜20 秒とテスト本体 22.5〜24.1 秒から、起動待ち 1 秒未満とテスト本体 17.8〜19.1 秒になった（2026-11-03、122 件）。

ブラウザのインストール（Dockerfile のレイヤーキャッシュと `--only-shell`）は `../slim-devcontainer/plan.md` の Phase 1 に統合済みで、本計画では扱っていない。

## 決定事項

- **起動済みサーバーの再利用:** CI 以外では、ポート 4173 で待ち受けているサーバーを使い、ビルドを省く。起動していなければ従来どおりビルドする。古いビルドに対してテストが通るリスクは、`testing-e2e.md` の Setup に「アプリのコードを変えたら preview を起動し直す」と書いて扱う。
- **`webServer.timeout` を 180 秒に短縮:** 従来の約 2.8 時間では、ビルドが固まっても失敗として表に出ない。起動待ちは 15〜20 秒なので十分な余裕がある。
- **トレースを既定で記録しない:** 従来の `retain-on-failure-and-retries` は、失敗時に残すために全テストを記録しており、テスト本体の約 25% を占めていた。失敗の調査は `pnpm test:e2e --last-failed --trace on` で失敗したテストだけ再実行する（`testing-e2e.md` の Debugging に記載）。

## 見送り案

- **ワーカー数を増やす（6・8）:** 定常状態では 4 ワーカーと差がなかった（下記の計測）。テスト時間の総和は増えており、preview サーバー・Postgres・ブラウザが 8 コアを取り合っている。当初は「ワーカー数が最大の要因」と判断したが、マシンが混んでいた時間帯の計測によるもので、計測をやり直して撤回した。
- **`fullyParallel` でファイル内も並列にする:** 定常状態で 18.2〜18.9 秒と、並列なし（17.8〜19.1 秒）と差がない。そのうえ `workbook_order.spec.ts` の並べ替えテスト同士が同じ配置データを更新し、競合で失敗した（`Expected: 35 / Received: 45`）。
- **ログイン状態の使い回し（`storageState`）:** ログイン 1 回は中央値 0.19 秒（10 回、179〜282 ms）で、beforeEach でログインするテストは 1 回の実行あたり 46 件だった。全部置き換えてもテスト時間の総和で約 9 秒、4 ワーカーの実時間では 2〜3 秒の短縮にとどまり、setup プロジェクトと複数ファイルの変更に見合わない。
- **トレースを `on-first-retry` ＋ `retries: 1` にする:** 失敗時に自動でトレースが残るが、タイミング依存のテストがリトライで成功扱い（flaky）になり埋もれる。
- **tester-army/e2e に置き換える:** 実体は `playwright-core`（1.64.1 で固定）の上に独自ランナーと、自然言語で操作する AI エージェントを載せたもので、ブラウザ操作の速さは変わらず、速度の主張もない。移行ガイドでは Playwright の 185 機能中 55 が未サポートで、`page.on('request')`・`browser.newContext(devices)`・判定関数付きの `waitForResponse`・`waitForFunction`・Trace Viewer・UI モードが使えない。`getByRole` の名前の文字列指定が既定で完全一致になり、ずれると否定のアサーションが素通りする。1.0 前で、エージェント手順には CI に LLM の API キーが要る。
- **他のフレームワークに置き換える:** 2026 年のベンチマークでは、Playwright が Cypress の約 1.45 倍・Selenium の約 1.85 倍速く、上回るものは見つからなかった（いずれもベンダーの記事）。Puppeteer はテストランナーを持たず、Vitest Browser Mode は内部で Playwright を使うコンポーネントテスト向けである。
- **Stagehand に置き換える:** AI エージェント向けのブラウザ操作 SDK で、テストランナーではない。操作のたびに LLM を呼ぶため、むしろ遅くなり費用もかかる。
- **Lightpanda に置き換える:** 2026-10-02 に 1.0 が発表されたとする記事があるが、npm の README はまだ CDP 対応を WIP としている。レイアウトを計算せずスクリーンショットも撮れないため、`navbar.spec.ts` の `boundingBox()` や `toBeVisible()` / `click()` の表示判定、ダークモード・カスタムカラーの検証が信用できなくなる。
- **Rust 製ツールに置き換える:** thirtyfour や chromiumoxide にはテストランナー・trace viewer・codegen がない。時間の大半はブラウザとアプリサーバーの待ちなので、ドライバーを Rust にしても短縮効果はほぼない。
- **ブラウザを別コンテナに出す（`playwright run-server` ＋ `connectOptions.wsEndpoint`）:** devcontainer からブラウザと依存ライブラリはなくなるが、公式イメージの取得、preview の `0.0.0.0` 待ち受け、ファイアウォールの調整が要る。インストールの遅さは `slim-devcontainer` の Phase 1 で解消する見込み。
- **`webServer` を `pnpm dev` に切り替える:** ページごとの初回コンパイルで遅延が出るうえ、依存パッケージの再最適化による再読み込みでテストが不安定になる。本番ビルドとの差異も生じる。
- **E2E 時だけアダプタを切り替えて約 5 秒削る:** `vite build` のうち約 5.0 秒は `@sveltejs/adapter-vercel` の出力生成で `vite preview` は使わないが、`svelte.config.js` に環境変数の分岐が増える。サーバーの再利用で 2 回目以降はビルド自体を省ける。

## 計測

環境は 8 コアの devcontainer（OrbStack）。`PLAYWRIGHT_JSON_OUTPUT_NAME=... pnpm exec playwright test --reporter=json,line` に CLI オプションを付けて実行し、JSON の各テストの開始時刻から起動待ちとテスト本体を分けた。

定常状態の比較（2026-11-03、preview を起動したまま、条件の順序を入れ替えて 4 巡、122 件。負荷が大きく揺れた 1 巡目は除く）:

| 条件                             | テスト本体    | テスト時間の総和 |
| -------------------------------- | ------------- | ---------------- |
| 4 ワーカー・トレースあり（従来） | 22.5〜24.1 秒 | 63〜69 秒        |
| 6 ワーカー・トレースあり         | 22.0〜23.6 秒 | 83〜86 秒        |
| 6 ワーカー・トレースなし         | 16.6〜17.1 秒 | 58〜60 秒        |
| 4 ワーカー・トレースなし         | 17.3〜17.8 秒 | 47〜49 秒        |
| 採用後の設定（3 回）             | 17.8〜19.1 秒 | 48〜53 秒        |
| 採用後の設定＋`--fully-parallel` | 18.2〜18.9 秒 | 70〜73 秒        |

- 1 巡目は同じ条件でも大きく遅かった（4 ワーカー・トレースありで 42.7 秒）。preview を起動した直後の 1〜2 回も 45 秒前後だった。マシン全体の負荷か、サーバーのウォームアップかは特定していない。
- 当初（2026-11-03 の午前）のベースラインは起動待ち 19.8 秒・テスト本体 69.5 秒・合計 89.5 秒で、途中で作業ツリーが `ac0a3f98` に切り替わるなど他の負荷と重なっていた。その時間帯の比較から出した「ワーカー数が最大の要因」という結論は、上記の計測で撤回した。
- preview なしの初回（ビルドを含む）は、起動待ち 19.7 秒・テスト本体 44.9 秒だった。
- 単体で測ると `prisma generate` は約 2.0 秒、`vite build` は約 15.2 秒。
- 最も遅いテストは `problems_contest_table` と `submission_status` の「再読み込み後も保持される」系で各約 13 秒。`/problems` の読み込みが 1 回約 4 秒かかっている。

## 検証結果

- **サーバーの再利用:** preview なしでは従来どおりビルドから実行した（`dark_mode.spec.ts:62` が 1 件失敗。下記の残課題）。preview を起動した状態では起動待ちが 0.8 秒になり、ビルドのログは出なかった。
- **トレースなし:** 採用後の設定で全件を 3 回実行し、すべて成功した。`navbar.spec.ts` と `dark_mode.spec.ts` を `--repeat-each=10` で実行し、すべて成功した。`pnpm test:e2e --last-failed --trace on` が引数を Playwright に渡すこと、`--trace on` で `trace.zip` が出力されることを確認した。
- `pnpm lint`・`pnpm check`・`pnpm test:unit`（2994 件）・`git diff --check` は成功した。
- 変更は設定 1 ファイルとドキュメントのみで、AGENTS.md のクロスレビュー条件に当たらないため、AI レビューは実施していない。
- 未確認: CI での挙動（E2E は `ci.yml` でコメントアウトされたまま）、8 コア以外のマシンでの計測。

## 残課題

- **タイミング依存のテスト 3 件:** 高速化で表に出やすくなる。今回の検証で再現しなかったため修正していない。
  - `navbar.spec.ts:42`: ハンバーガーメニューをクリックしてもメニューが開かないことがある（全件 29 回と単体 10 回のうち 1 回）。ハイドレーション完了前のクリックとみられる。
  - `dark_mode.spec.ts:62`: クリック直後に `getAttribute('class')` を 1 回だけ読むため、切り替えの反映前に読むと失敗する（全件 29 回と単体 10 回のうち 1 回）。自動で再試行するアサーションにすれば解消する見込み。
  - `votes.spec.ts:107`: 検索直後に `isVisible()` を 1 回だけ確かめ、結果の描画が間に合わないと「DB に該当なし」として黙ってスキップする（全件 29 回のうち 1 回）。
- **`/problems` の読み込みの重さ（1 回約 4 秒）:** アプリの性能の問題として別途扱う。
- **ブラウザのインストール:** `../slim-devcontainer/plan.md` の Phase 1。同計画の `Dockerfile` 例は 2026-09-30 時点の値（Node 24、Playwright 1.63.0）で、現在は Node 26、Playwright 1.64.1、ブラウザは `chromium-1248`（400MB）と `chromium_headless_shell-1248`（276MB）である。
- **CI での E2E 実行:** `ci.yml` では E2E がコメントアウトされたまま。
