# SvelteKit 3 / adapter-vercel 7 移行調査

## 概要

[移行計画](./plan.md) の根拠となる調査。Renovate の [#4105](https://github.com/AtCoder-NoviSteps/AtCoderNoviSteps/pull/4105)（Kit 2.70.3 → 3.0.0）と [#4104](https://github.com/AtCoder-NoviSteps/AtCoderNoviSteps/pull/4104)（adapter-vercel 6.3.4 → 7.0.0）は、それぞれ片方だけを更新していたため 2026-10-03 時点で Node 24 CI の Build が失敗し、現在は closed。2026-10-18 時点で open の依存 PR は [#4115](https://github.com/AtCoder-NoviSteps/AtCoderNoviSteps/pull/4115)（Superforms 3.0.0）のみ。
調査は 2026-10-03 に始め、10-06・10-18 に追加した。基準は 2026-10-18 JST の `origin/staging`（`f02b7238`）。方法は manifest・配布コード・ソースの静的調査と、alias の置換をリポジトリのコピー上で試した検証。2026-10-19 には Kit 3 の spike で build・unit test・lint・check を実行した（→「Kit 3 の spike」）。その後、branch `#4192` で E2E の全件を流し、Kit 3 を仮に deploy した preview で手動確認も行った（2026-10-21、plan の「手動確認」）。要点は [summary.md](./summary.md) にまとめた。
前回までの誤認と古くなった記述は、末尾の「前回調査からの訂正」にまとめた。

## Superforms 3.0.0（#4115）

#4115 は 2.31.0 → 3.0.0 の依存・lockfile 更新（2ファイル）のみで、2026-10-18 に staging へマージされた（`dc9f2471`）。マージ前に preview deploy での5画面の確認と、手元の E2E（5本の spec・56件、すべて成功）を行った。Superforms 2.x は bugfix のみの維持になり、Kit 3 には v3 が必須（公式の upgrade paths）。
head `5833c1d0`（2026-10-18 に staging `f02b7238` の上へ rebase）の lockfile の差分は、Superforms 本体と optional 依存の更新に限られる（ArkType 2.2.2 → 2.2.8、@ark/schema・@ark/util 0.56.1 → 0.56.7、arkregex 0.0.7 → 0.0.13、Vine 3.0.1 → 4.4.0・compiler 3.0.0 → 4.2.0 と新規の @poppinss/types 1.2.1、camelcase 8 → 9、Valibot 1.4.2 → 1.5.0・@valibot/to-json-schema 1.7.1 → 1.8.0、Joi 17.13.4 → 17.13.8、TypeBox 1.3.4 → 1.4.2）。2.31.0 の optional 依存が引いていた `effect@3.22.2` は消え、override（`effect@>=3.0.0 <3.20.0` → 3.22.3）の解決先 3.22.3 に統合された。devalue・esm-env と、Kit・Svelte・Vite の解決版は変わらない。
この lockfile を pnpm 12.14.0 の `install --lockfile-only` で再解決しても書き換えは出ず、supply-chain policy の検査も通った。Kit 2 の CI 成功は、Kit 3 での成功を意味しない。

### Kit 3 の spike（2026-10-19）

staging（`e3d1145c`、PR A・PR A2 のマージ後）のコピーで `npx sv@1.1.1 migrate sveltekit-3` を Phase 1 の範囲（`svelte-config`・`lib-alias` と、自動で実行される前提タスク `package-json`・`tsconfig`）で実行し、Kit 3.1.0・adapter-vercel 7.0.1 に上げた。

- `sv migrate` のタスクは12個: `package-json`・`tsconfig`（前提）、`svelte-config`、`environment`、`paths`、`external-redirects`、`shallow-routing`、`params`、`imports`、`lib-alias`、`app-state`、`collect-migration-instructions`（自動化できない作業を `MIGRATION_TASKS.md` に書き出す）。前提タスクは `--tasks` で指定できず、自動で実行される。
- 出力のうち、そのままでは使えなかったもの:
  - `svelte.config.js` の `vitePlugin` を `sveltekit({ vitePlugin: { dynamicCompileOptions } })` に移した。Kit 3 は `config.vitePlugin` を削除しており、`svelte-kit sync` が `config_option_removed_vite_plugin`（「Pass `vite-plugin-svelte` options directly to the `sveltekit(...)` Vite plugin」）で失敗する。`dynamicCompileOptions` は `sveltekit({...})` の直下に置く。
  - Kit と adapter を `^3.0.0`・`^7.0.0` の範囲指定にした（本プロジェクトは版を固定する）。
  - 実在しない `src/lib/index.js` への bare `#lib` を `package.json#imports` に足した。
  - `lib-alias` が Markdown の中の `$lib` まで `#lib` に置換した。`architecture.md` の「組み込みの `$lib` を削除」が「組み込みの `#lib` を削除」になって文意が壊れ、過去の dev-notes 8件も書き換えた。
  - 既存のコメントを無関係な位置へ移し、`//` のコメントを `/* */` に書き換えた。
- `tsconfig.json` は `extends: "$app/tsconfig"` になり、`allowJs`・`checkJs`・`isolatedModules`・`moduleResolution: bundler`・`skipLibCheck`・`verbatimModuleSyntax` などが削られた。生成された `node_modules/$app/tsconfig.json` がこれらをすべて提供し、`paths` は空なので、削っても結果は同じ。`types` は extends で置き換わるため `$app/types` を自分で含める。
- 結果: build（`.vc-config.json` は `nodejs24.x`・`hnd1`・memory 3008・maxDuration 30、framework は sveltekit 3.1.0）・unit test（2726件）・lint は成功。check は 20 errors で、すべて Phase 2 の項目（`$app/environment`、`Handle`・`SubmitFunction` の型の移動、`$app/stores`、不要になった `@ts-expect-error`、`resolve()` の引数、汎用の `Actions` 型での `params`）。内訳は計画の Phase 2 に記載。警告は Kit 2 と同じ 30件。
- `$app/environment` は Kit 3 の型からは消えている（`Cannot find module`）。build は通るが、Phase 2 で `$app/env` に置き換える必要がある。
- lockfile からは Kit 2 の経路の `devalue@5.8.1` が消え、`cookie` は 2.0.1 になった。

Phase 2（branch `#4192`）の作業で分かった Kit 3.1.0 の挙動:

- `resolve()` は、`/` で始まる引数を route ID として扱い、`(group)` を除いて `[param]` を埋める。`?`・`#` 以降はそのまま残る。それ以外は pathname として base を前に付ける。型が受け付けるのは、既知の route ID・pathname と、それに `` `?${string}` ``・`` `#${string}` `` を付けたテンプレート文字列だけで、`string` は渡せない。route ID に `/signup` のようなグループを含まない形は無く（`/(auth)/signup`）、pathname は先頭に `/` を付けない。
- `goto()` は非推奨の `replaceState` を `replace` として受け付け続ける（`opts.replace ?? opts.replaceState`、開発時に警告）。
- 実行時の `$app/environment` は `../env/index.js` を再 export するだけで残っている。型は消えているので、import は `$app/env` に変える必要がある。テストで `$app/env` を mock すると、`$app/environment` から import するコードにも効く。
- `page.url` は型の上で読み取り専用で、`searchParams` は `ReadonlyURLSearchParams`。`URLSearchParams` や `URL` を受け取る関数には、そのまま渡せない。
- route 専用でない汎用の `Actions` 型（`@sveltejs/kit`）では、`params` の値が `string | undefined` になる。

Phase 3 の E2E で確かめた挙動（Kit 2 との比較は staging のコピーで実行）:

- enhanced の form action が `fail(400)` を返すと、Kit 3 は HTTP 400 を返す（Kit 2 は 200）。JSON で返すかの判定は `accept` ヘッダーのままで、本文の ActionResult は `{ type: 'failure', status: 400 }`。
- 別ページ宛の enhanced action（Header のログアウト）は、失敗しても action のページへ遷移する。未ログインでログアウトすると、Kit 3 は `/logout` の `load` の redirect を経て `/` に着く（Kit 2 は元のページに留まっていた）。
- ゲストログイン（`AuthForm` が `fetch` で直接 POST する）は、成功時の応答が HTTP 200 の redirect で Kit 2 と同じ。失敗時は Kit 3 では HTTP 400 になり、`response.ok` が false なのでログイン画面に留まる。Kit 2 では 200 が返り、失敗してもホームへ遷移していた。
- 本アプリは `handleError` を定義していない。Kit 3 の既定の実装は、予期しない例外（500）のスタックはサーバーに記録し、404・403 などの想定済みのエラーは記録しない。500 の `+error.svelte` には `Internal Error` が出る。
- session cookie は Kit 3（cookie v2）でも `path: /`・`httpOnly`・`secure`・`sameSite: Lax` のまま。

### ビルド時間とサイズ（2026-10-19）

Kit 3 でビルド速度やサイズの恩恵があるかを測った。結論は、恩恵は無く、どちらもわずかに悪化するが実用上の差は無い。Kit 3 の移行の理由は、保守の継続（adapter 7 が Kit 3 を前提にする）と開発時の検査の強化（server-only の保護・`resolve()` の型など）で、性能ではない。

比較は、Kit 2 の `staging`（`e3d1145c`）のコピーと、Kit 3 の `#4192`（`444e4daf`）。同じマシンで `pnpm build` を交互に3回ずつ実行した。初回表示の JS は、それぞれの `vite preview` を Playwright で開き、`resourceType` が script の応答の本文を合計した（未ログイン）。gzip は level 9 で自前に計算した。

| 項目                                        | Kit 2                 | Kit 3                 | 差               |
| ------------------------------------------- | --------------------- | --------------------- | ---------------- |
| `pnpm build` の時間（3回）                  | 10.8・12.3・10.0 秒   | 14.0・15.3・12.9 秒   | 平均 +3 秒       |
| うち Vite が報告する時間（2段の合計）       | 約 8.0 秒             | 約 5.8 秒             | −2 秒            |
| `/` の初回表示の JS                         | 23本・234.2 KB (gzip) | 25本・238.0 KB (gzip) | +3.8 KB（+1.6%） |
| `/problems` の初回表示の JS                 | 39本・263.4 KB (gzip) | 42本・267.3 KB (gzip) | +3.9 KB（+1.5%） |
| client JS の合計（`_app/immutable`）        | 76本・396.8 KB (gzip) | 79本・398.9 KB (gzip) | +0.5%            |
| framework の入口（`immutable/entry`）       | 3.8 KB (gzip)         | 2.4 KB (gzip)         | −37%             |

- build は、Vite の段は速くなったが、残りの処理（adapter による Vercel 向けの出力などと推測、内訳は未計測）が長くなり、全体で約3秒遅い。build 全体が十数秒なので CI への影響は小さい。
- 入口のファイルは小さくなったが、chunk が2〜3本増えており、コードが別の chunk に移っただけで、ブラウザーが読む量は約4 KB 増えた。
- 1台・3回の計測で、配信時の圧縮（Vercel 側）は再現していない。Kit 2 と Kit 3 の相対差として扱う。

依存の変化（`staging` と `#4192` の `pnpm-lock.yaml` の `packages` を比較）:

- lockfile 全体は 878 → 872 パッケージ。消えたのは9件（`@sveltejs/kit@2.70.3`・`@sveltejs/adapter-vercel@6.3.4`・`@sveltejs/acorn-typescript@1.0.10`・`@types/cookie@0.6.0`・`cookie@0.7.2`・`devalue@5.8.1`・`kleur@4.1.5`・`picomatch@4.0.4`・`set-cookie-parser@3.1.0`）、増えたのは3件（`@sveltejs/kit@3.1.0`・`@sveltejs/adapter-vercel@7.0.1`・`cookie@2.0.1`）。

## alias から subpath imports への置換

### Kit 3 での alias の扱い

- 組み込みの `$lib` と `files.lib` は削除される。残した `files.lib` はエラーになる。
- `$lib` は alias で維持できる。Kit 3.0.0 のソースは、組み込みの `$lib` が無いときのエラーで「To keep using `$lib`, add `alias: { '$lib': 'src/lib' }` to your SvelteKit config.」と案内する。alias は Vite の解決と tsconfig の `paths` の生成に引き続き使われる。
- ただし `kit.alias` 自体が deprecated で、build 時に「The `alias` option is deprecated, and will be removed in a future version of SvelteKit. Use subpath imports instead」という趣旨の警告が出る。`@`・`$features` も同じ扱い。削除時期は示されていない。
- 3.0.0 → 3.1.0 でこれらの扱いに変化はない（→「対象バージョン」）。

### Kit 3 が `$lib` を `#lib` に変えた理由

Kit の issue・PR・docs から読み取った経緯。

- **独自の alias より標準の仕組み:** 発端は Rich Harris の issue [#16182](https://github.com/sveltejs/kit/issues/16182)「replace `$lib` with `#lib`」（2026-06-26）。`$lib` は Kit 独自の alias だが、`package.json` の `imports` は TypeScript を含めて広く対応された標準の仕組みなので、`src/lib` はそちらで指す。`$app/*` は Kit の提供物、`#lib/*` は利用者のコード、と役割も分かれる。[PR #16360](https://github.com/sveltejs/kit/pull/16360) が 2026-07-17 に version-3 へ入った。
- **`$lib` の実害:** Vite を通らない場所（`vite.config.ts`・ESLint の設定・Node のスクリプト）では `$lib` が解決されず、Node が package 内部の名前として認める `#` 始まりの名前と混在しがちだった（[#15234](https://github.com/sveltejs/kit/issues/15234)）。monorepo では、ライブラリ側のコードの `$lib` が実行中のアプリの `src/lib` に解決される問題が2021年から残っていた（[#2879](https://github.com/sveltejs/kit/issues/2879)、2026-08-03 に close）。`package.json#imports` は import したファイルに最も近い `package.json` を基準に解決するので、この問題が起きない。
- **`#` である理由:** Node の規格で、`package.json` の `imports` の名前は `#` で始まる必要がある。Vite と TypeScript は設定なしで解決する（[`$lib` の docs](https://github.com/sveltejs/kit/blob/main/documentation/docs/98-reference/26-%24lib.md)）。`lib` という名前は `$lib`・`src/lib` との連続性によるもので、技術的な必然はない。
- **`alias` の非推奨:** Rich Harris の issue [#16468](https://github.com/sveltejs/kit/issues/16468) が「People really should just be using subpath imports」「Using The Platform」として `alias` 設定を非推奨にした（[PR #16470](https://github.com/sveltejs/kit/pull/16470)、警告のみで動作は継続）。alias を使い続けたい場合の代替として Vite の `resolve.tsconfigPaths` が挙げられている。
- **拡張子が必須になった理由:** 当初は tsconfig の `paths` にも `#lib` を入れて拡張子なしで書けたが、Vite を通らない場合（esbuild でまとめる場合など）に「it'll break in weird ways」ため「More harm than good」として外された（[PR #16736](https://github.com/sveltejs/kit/pull/16736)）。その結果、Node の標準どおりに拡張子が必要になった。PR の本文は拡張子の必須化そのものの理由を明記しておらず、これは `paths` を外したことからの帰結と読んだ。Playwright のランナーで `#lib` が解決できないのも、この「Vite を通らない場合」に当たる。

単一アプリの本プロジェクトでは monorepo の問題は関係しない。得られる利点は、Vite・Vitest・TypeScript・tsx（seed）が同じ標準の仕組みで import を解決するようになることと、`$features` の置換（PR A2）を含めて `alias` 非推奨の流れに沿えること。

### 置換の対象

| ------------ | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |

| specifier    | 676（`from` 651・`vi.mock` 25）                                                                                  | 286（`$features` 284 = `from` 277・動的 import 1（`src/app.d.ts` の型参照）・`vi.mock` 6、`@/features` 2） |

### 拡張子の規約

- TS モジュールは `.js`（`$lib/types/task` → `#lib/types/task.js`）。TypeScript と Vite が `.ts` の実体に対応付ける。
- コンポーネントは `.svelte` のまま。
- runes モジュール（実体が `.svelte.ts`）は `.svelte.js`（`$lib/stores/local_storage_helper.svelte` → `#lib/stores/local_storage_helper.svelte.js`）。末尾の `.svelte` を拡張子と見なすと型エラーが5件出たため、[codemod_subpath_imports.py](./codemod_subpath_imports.py) は実在ファイルで拡張子を判定する。
- 既存の `.js` 指定（2件）はそのまま。
- E2E の spec では `#lib` を使わず、相対 import のままにする。Playwright のランナーは `#lib/*.js` を `src/lib/*.js` に解決するが `.ts` の実体に対応付けないため、`Cannot find module` で失敗する（2026-10-18 に実測）。
- `package.json#imports` には `#lib/*` と `#features/*` だけを置き、実在しない `src/lib/index.js` への bare `#lib` は追加しない。

### 再流入の防止

- `$lib`: Kit 2 は `$lib` を組み込みで解決するため、置換後に新しいコードへ `$lib` が混ざっても Kit 3 に上げるまで気付かれない。`.oxlintrc.json` の `no-restricted-imports`（`{ "patterns": [{ "regex": "^\\$lib(/|$)" }] }`）で `.ts` の `$lib` import を検出でき、`#lib` は通ることを oxlint 1.88.0 で確認した。`.oxlintrc.json` は `.svelte` を対象外にしているので、`.svelte` は ESLint の同じ規則で検出し、こちらも `$lib` を検出して `#lib` を通すことを確認した。構文ごとの検出範囲も実測した。oxlint（`.ts`）は `import type`・`export … from`・`export * from`・動的 `import()` を検出し、ESLint（`.svelte`）は `import type` を検出するが動的 `import()` は検出しない。`vi.mock('$lib/...')` は関数呼び出しなので、どちらの規則でも検出されない。この穴は、alias の変更時と PR B の spike 前に grep で残りが 0件であることを確かめて補う。
- `$features`・`@`: `svelte.config.js` から alias を外すと、残った `$features/...` の import は `svelte-check` で `Cannot find module` になる（コピーで確認）。リント規則は要らない。
- 作業中の別 branch は、rebase 後に codemod を再実行すれば新規ファイルの alias も置換される。衝突するのは、置換した import 行かその隣接行を同じ branch が変更している箇所に限られる。

### 気付いた既存の問題

`src/features/tasks/components/contest-table/TaskTableBodyCell.svelte` が `@/features/votes/components/VotableGrade.svelte` を import している。tasks feature から votes feature への import で、AGENTS.md が禁じる feature 間 import にあたる。`@` alias で見えにくくなっていた。置換しても違反は残る。
